# 004 — Development environment: Nix

Status: accepted (2026-10-30)

## Context

The project needs Flutter, a JDK, the Android SDK and NDK, firebase-tools and
Node.js, at versions that agree with each other, on the author's Mac, on CI and
for anyone else running their own instance.

## Decision

All tools come from a Nix flake (`flake.nix`, pinned by `flake.lock`).

- **`nix develop`** (or direnv with `use flake`) gives a shell with Flutter,
  JDK 21, the Android SDK, firebase-tools and Node.js. Nothing needs to be
  installed globally. JDK 21 is the minimum for the Firebase emulators and
  also runs Gradle.
- **Node.js 24**, the newest runtime Cloud Functions supports outside
  preview (until October 2028). The Firebase JS SDK 13 and its rules test
  library need at least 24.12. `functions/package.json` (`engines`) sets the
  deployed runtime and must match `flake.nix`.
- **CI jobs use shells with exactly what the job needs**, nothing extra.
  In particular, only jobs that build Android get the Android SDK, which is
  several gigabytes and not in the public Nix cache:

  | Shell | Contents | Used for |
  |---|---|---|
  | `default` | everything | local development |
  | `dart` | Flutter | domain package and app unit tests, web build |
  | `android` | Flutter, JDK, Android SDK | APK builds |
  | `functions` | Node.js | Functions unit tests and build |
  | `emulators` | Node.js, JDK, firebase-tools | rules tests, Functions integration tests |
  | `integration` | Flutter, Node.js, JDK, firebase-tools, Chrome, chromedriver | app tests against the emulators |

  `default` also includes Chrome and chromedriver. The browser is Google Chrome
  on macOS (Chromium isn't packaged there) and Chromium on Linux, with a
  chromedriver of the same version; `CHROME_EXECUTABLE` points Flutter at it.

  `nix develop` keeps the caller's `PATH`, so tools installed on the machine
  can leak into a shell locally; `nix develop -i` checks a shell in isolation.
  CI runners have no such tools.
- **`nix run`** launches the app. Apps are thin scripts in `scripts/`, each
  run with exactly the tool sets it needs:
  - `nix run` (default): Firebase emulators on a `demo-` project in the
    background, the Functions compiler in watch mode, and the web app with hot
    reload in the foreground. Emulator data persists between runs in
    `firebase/.emulator-data/`.
  - `nix run .#android` (once the Android app exists): the dev flavor on a
    connected Android device or emulator, pointed at the emulators on this
    machine.
  - `nix run .#emulators`: the Firebase emulators only.
  - `nix run .#test`: all test suites.
  - `nix run .#screenshots`: screenshots of the seeded app at phone and tablet
    sizes.
- **CI** runs the same commands through `nix develop -c …`, so CI and local
  development use identical tool versions ([008](008-ci.md)).

The Android SDK comes from nixpkgs `androidenv`. It lives in the read-only Nix
store, so Gradle can't download missing components: the SDK platform,
build-tools and NDK versions that Flutter's Gradle plugin expects are listed
explicitly in `flake.nix` and must be updated together with Flutter.

The browser for web development isn't provided by Nix on macOS. The web app is
served with Flutter's `web-server` device and opened in any browser.

## Consequences

- Updating Flutter means updating nixpkgs (`nix flake update`), then checking
  the Android versions Flutter expects (`FlutterExtension.kt` in the Flutter
  SDK) against `flake.nix`.
- Flutter's own dependencies (pub packages, Gradle artifacts) are still fetched
  by Flutter and Gradle, not Nix. `nix run` targets are convenient launchers,
  not pure builds. Likewise, firebase-tools downloads the emulator binaries
  and the Emulator UI on first use, into `~/.cache/firebase/emulators/`.
- Release builds may later get pure Nix builds (`buildFlutterApplication` for
  web) if reproducibility matters.
